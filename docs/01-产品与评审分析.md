# AI自适应Web漏洞智能探测与绕过检测系统 — 产品定位与竞赛评审视角分析

> 文档类型：产品定位澄清 + 竞品/创新拆解 + 答辩评审预判（分析类，非设计类）
> 分析依据：图1 架构逐层拆解说明、图2 团队分工表、图3 系统架构图，及用户原话「相当于是 AI 自己去挖 nday 漏洞的一个系统」
> 说明：本文所有判断基于所给材料的**定性推断**，不含任何实测性能数据、benchmark 或外部引用来源；凡属推断处均已标注。涉及安全工具的内容仅作产品与合规层面讨论，不含可用于攻击真实系统的载荷或操作步骤。

## 核心结论（先看）

1. **项目当前最大的风险不是技术，是"说错话"**：用户口头说的「AI 挖 nday」与材料写的「不主打 0day、主打 WAF 环境下自适应绕过探测已知漏洞」是两套口径，且前者概念不成立。若不统一，评委会用「漏洞挖掘/0day」的标准来衡量一个「已知漏洞类型探测 + WAF 绕过」的系统，落差极大。
2. **实质定位**：面向授权目标的、WAF 环境下的**已知漏洞类型探测（验证）辅助工具**，创新载体是"以 HTTP 响应为反馈状态、由本地大模型在线决策下一轮探测载荷变形"的闭环，外加"过程可视化 + 证据链留痕 + 标准化报告"的产品完整度。
3. **创新成色取决于三份证据**：消融实验（去掉反馈/去掉模型还行不行）、未见过的 WAF 规则上的泛化测试、轮次—成功率收敛曲线。有这三样，创新站得住；没有，就容易被判成"套壳调大模型"或"字典 + 提示词模板"。
4. **与 sqlmap 的正确关系**：不是"超越/替代"，而是"WAF 场景下的补充与增强"。定这个位，答辩最稳。
5. **人力风险高度集中在 1 号**（创新成立与否全压在他一人），且团队呈"前期偏闲、答辩前一周全挤在一起"的节奏风险。

## 1. 定位澄清（最重要）

### 1.1 五个概念的区别

| 概念 | 准确含义 | 对应关键动作 | 本项目是否涉及 |
|---|---|---|---|
| **0day** | 未公开、厂商未知、无补丁的漏洞 | 漏洞研究 / 发现：fuzzing、代码审计、二进制分析、原创 PoC | **否**，材料已明确「不主打 0day」 |
| **nday（已知/已公开漏洞）** | 已公开、已有编号（CVE/CNVD 等）、通常已有补丁或检测规则的漏洞 | **复测、验证目标是否仍受影响**、POC 验证、补丁核查 | 弱相关，见 1.2 |
| **漏洞发现（Discovery）** | 找到前人不知道的漏洞，产出"新知识" | 研究、原创性验证 | **否** |
| **漏洞探测 / 验证（Detection & Verification）** | 判断某个目标**是否存在**某类或某个已知漏洞 | 发探测载荷 → 采响应 → 判定 → 出证据 | **是，这是项目实质** |
| **WAF 绕过（Evasion）** | 不改变漏洞本身，只改变载荷的"外观"（编码、混淆、等价变换等），使其穿过防护规则匹配 | 投递 / 规避技术 | **是，这是项目创新载体** |

一句话记住分类：**"发现"是产出新知识，"探测/验证"是判断已知知识在目标上是否成立，"绕过"是让探测流量不被中间设备挡住**。三者不在同一层。

### 1.2 「AI 自己去挖 nday」为什么不准确

- **"挖"字用错**：nday 是"已知漏洞"，已知的东西谈不上"挖"（发现）；对已知漏洞只能做"验证/复测/检出"。说"挖"会让人自然联想到"发现新漏洞"。
- **连 nday 都算不上**：本项目测的是 SQL 注入 / XSS / 文件上传这类**漏洞类型（弱点大类，CWE 层面）**，并未绑定任何具体 CVE/CNVD 编号或具体产品的已知漏洞实例。因此它严格来说是**"已知漏洞类型的自动化探测"**，比"nday 复测"还要再泛一层。
- **与材料自相矛盾**：材料里已写好边界「Web 渗透测试辅助工具、企业自测、等保自查、不主打 0day」，口头却说"AI 自主挖洞"，等于团队自己给出两套定位。
- **真正的创新点被这句话埋没了**：项目最值钱的是"闭环自适应的 WAF 绕过 + 过程可解释"，而不是"AI 挖洞"。用"挖洞"当标题，等于把强项藏起来、把弱项顶到评委枪口上。

### 1.3 表述不当在答辩中的具体风险

| # | 风险 | 触发场景与后果 |
|---|---|---|
| 1 | 概念一问即崩 | 评委问「你们挖出了哪个 CVE / 有没有原创 PoC」，答不上，直接被判定"夸大、不严谨"，全盘可信度受损 |
| 2 | 评判标尺被抬高 | 被按"漏洞挖掘/0day 研究"标准衡量（要求 fuzzing、代码审计、原创性），而项目实际是扫描器范畴，落差巨大 |
| 3 | 放大"套壳"质疑 | "AI 挖洞"是当下最容易被贴上"套壳 / 蹭大模型概念"标签的表述，主动送把柄 |
| 4 | 前后口径不一 | 申报书、PPT、讲稿、现场口述若不一致，评委认为"团队自己都没想清楚做什么" |
| 5 | 伦理与安全敏感 | "AI 自主挖洞/攻击"容易引发合规质疑；"授权自测辅助工具"则天然安全 |

### 1.4 建议的统一对外口径

**正式版（申报书 / PPT 首页 / 讲稿统一使用，一字不改）：**

> 本系统是面向**授权目标**的 Web 漏洞检测辅助工具：在存在 WAF 防护的场景下，通过**本地大模型对每轮探测响应做闭环反馈、自适应变形探测载荷**，提升对**已知漏洞类型**（SQL 注入、XSS、文件上传等）的检出能力并降低误判，用于企业自测与等保自查；**不涉及 0day 或未知漏洞挖掘，不用于未授权目标**。

**答辩口语版（一句话记住）：**

> "AI 不'挖'洞，AI 学'绕'——我们解决的是：有 WAF 挡着的时候，已知漏洞怎么还能被测出来、怎么把过程讲清楚。"

**用词替换表（供 2 号改讲稿、3 号改材料时逐条核对）：**

| 不要用 | 改成 |
|---|---|
| AI 挖漏洞 / AI 挖 nday / 自主挖洞 | AI 自适应探测 / 已知漏洞类型的自动化验证 |
| AI 发现漏洞 | AI 检出漏洞、识别出存在漏洞 |
| 攻击、打靶、拿下站点 | 探测、验证、授权测试 |
| 超越 sqlmap / 替代扫描器 | 对现有扫描器在 WAF 场景下的补充与增强 |
| 0day / 未知漏洞 | 已知漏洞类型、WAF 环境下的漏报问题 |

## 2. 目标用户、真实场景与核心痛点

### 2.1 目标用户分层

| 层级 | 用户 | 特征 | 与项目关系 |
|---|---|---|---|
| **主要** | 企业/单位内部安全自查人员、等保测评与合规自查的运维或安全工程师 | 有自查义务，但未必有专职渗透经验；需要**可留痕、可出报告**的结论 | 产品价值主张的核心对象 |
| **主要** | 无专业安全团队的中小开发团队（上线前自检） | 站点前挂了 WAF/云防护，扫不出东西就误以为"没漏洞" | 痛点最典型 |
| **次要** | 高校网络安全竞赛、教学/靶场实训 | 需要把黑盒过程**可视化、可讲解、可复现** | 大屏监控页与对比演示的直接受众，也是本项目的**实际评审场景** |
| **非目标** | 职业红队 / 漏洞研究员 | 已有 Burp + sqlmap + 手工经验与自研工具链 | 不是本产品的受众，答辩时不要拿他们当对标 |

> 判断（推断）：材料写"企业自测、等保自查"，但整套设计（大屏实时 payload、对比演示、四层架构图、4 人分工）明显更贴合**教学/竞赛作品**，而非商业化安全产品。建议答辩时把"企业自测"讲成**应用方向**，把"竞赛演示 + 方法验证"讲成**本作品定位**，不要反过来。

### 2.2 真实使用场景

| 场景 | 现状 | 本项目提供的价值 |
|---|---|---|
| **A. 上线前 / 等保自查** | 目标前面有 WAF，传统扫描器一扫全是拦截页，报告"未发现漏洞"——但这只是**没测到**，不是**没有** | 让探测载荷能穿过 WAF，暴露"绕过 WAF 后真实存在的漏洞"，把**假阴性**变成可确认结论 |
| **B. 合规留痕出报告** | 手工拼接请求包/响应包/证据链/风险等级，成本高、格式不统一 | 全量留痕（任务 / payload / 漏洞三张表）+ 自动产出对标等保测评风格的 PDF，证据链可追溯 |
| **C. 教学 / 竞赛演示** | WAF 绕过是黑盒经验，学生看不见"为什么这个变形能过" | 大屏逐轮展示"当前 payload → WAF 拦截标记 → AI 下一次怎么改"，把经验变成可讲解的过程 |

### 2.3 核心痛点与现有工具为何没解决好

| # | 痛点 | 现有工具为什么没解决好（定性推断） |
|---|---|---|
| 1 | **WAF 造成假阴性** | sqlmap/AWVS/ZAP 的探测载荷集是预定义的；遇到针对性 WAF 规则被整批拦截，扫描器要么报"无漏洞"要么报错退出。**"被拦"与"没洞"没被区分开**——这恰是本项目漏洞判定子模块要解决的 |
| 2 | **绕过靠人、不可复制** | 现有绕过高度依赖有经验的工程师手工试载荷、写 tamper 脚本；门槛高、难沉淀、换一个 WAF 规则就得重来 |
| 3 | **过程不透明、不可解释** | 扫描器是"批量跑字典"的黑盒，无法回答"为什么这次能过、WAF 规则是怎么被绕开的"；对自查报告与教学都缺说服力 |
| 4 | **误报与证据链** | 纯规则匹配误报偏高；报告证据需人工整理 |
| 5 | **联网与数据外泄** | 若用云厂商大模型做安全检测，请求包/响应包含 Cookie、Token、业务数据，企业不愿外传；比赛断网环境也无法调用 | 这是选**本地 Ollama** 的真实理由（**数据不出域 + 离线可用**），不只是"断网能跑" |

> 注意：痛点 5 是被材料轻描淡写、但**答辩时很能加分**的一条。建议把"离线推理"从"比赛应急措施"提升为"面向企业敏感数据的产品取舍"来讲。

## 3. 创新性拆解：真创新 / 工程整合 / 伪创新

> 分类标准：**真创新** = 方法层面有可辩护的新颖性，且可用实验证伪；**工程整合创新** = 单点不新，但端到端完整度构成产品价值；**伪创新** = 名不副实或只是口号，若不主动降调/补证据会成为扣分项。

### 3.1 真创新（相对可辩护，但必须配证据）

| 创新点 | 理由 | 评委要看到什么才算数（证据要求） |
|---|---|---|
| **以 HTTP 响应为反馈状态的闭环自适应生成** | 把"本轮被拦 / 触发 / 正常"作为状态回传给模型，由模型决定**下一轮**变形方向；不是预置字典一次性跑完。这是与静态 tamper 的本质分野 | ① 同一 WAF、同一注入点的**多轮迭代日志**（第1轮被拦 → 模型判定拦截类型 → 第2/3轮变形 → 命中）；② **消融实验**：去掉反馈后退化成随机变形，对比绕过成功率与收敛轮数 |
| **"WAF 拦截 vs 真正触发漏洞"的语义判别** | 区分这两类响应是消除假阴性的关键，规则关键词难以覆盖变形后的拦截页 | 一个小规模**标注样例集**（拦截 / 触发 / 正常三类）+ 判别混淆矩阵，展示模型分辨能力 |
| **离线、数据不出域的本地推理闭环** | 把大模型放进"发包—反馈—再生成"的自动控制回路且全程本地，兼顾断网与敏感数据 | 断网环境下完整跑通；**网络抓包**证明零外部 API 调用 |

> 提示（推断）：这三条的"新颖性"来自**把 LLM 用作闭环控制器里的策略函数**，而非 LLM 本身。若 1 号能拿出消融实验，成色即成立；拿不出，评委会把它降级为"工程整合"。

### 3.2 工程整合创新（有价值、非原创，是"产品完整度"而非"技术突破"）

| 整合点 | 理由 |
|---|---|
| 5 子模块串成端到端产品 | 爬虫采参 → 本地推理 → 发包验证 → 双重判定 → 反馈迭代，把 1 号的脚本"包装"成 Web 平台可调用、可监控、可导出 |
| 探测过程大屏可视化 | 实时展示"AI 当前正在测试的 payload + WAF 拦截标记"，把黑盒经验变成可解释、可讲解的过程；**对竞赛演示是实打实的加分项** |
| 规则 + AI 语义双重判定 | 用规则保底、用语义降误报，是稳健的工程设计 |
| 全量留痕 + 标准化 PDF 报告 | 任务表 / payload 表 / 漏洞表形成证据链，对标等保测评报告风格，直接对应"出报告"这一真实需求 |
| 一键部署包 + 并发/超时控制 | 降低复现成本，让评委/用户能自己跑 |

> 定位建议：**把这些讲成"我们做的是一个完整、可用、可复现的系统"，而不是"我们发明了这些技术"**。诚实反而加分。

### 3.3 伪创新 / 易被质疑（建议主动降调或补齐证据）

| 说法 | 为什么会被质疑 | 补齐/降调方式 |
|---|---|---|
| "AI 挖漏洞 / 自主挖 nday" | 名不副实，见第 1 部分 | **直接删除**，换成统一口径 |
| "大模型生成 payload" | 若本质是把已有绕过技巧写进提示词让模型复述或排列组合，就是"字典 + 提示词模板"，易判**套壳** | 证明载荷由**本轮响应**驱动而非从预置列表抽取：用**未预设过的 WAF 规则 / 新变形组合**测试并展示泛化 |
| "自适应、边测边学" | 若循环里只是换载荷、策略不收敛（成功率不随轮数提升），就是"随机重试"包装成"学习" | 画出**轮次—累计检出率 / 绕过成功率曲线**，证明迭代确实有效；否则改称"自适应重试" |
| "降低误报" | 无量化即为口号 | 标注集 + 误报率/漏报率 + 与纯规则基线的对比；样本不足就如实写"小样本验证，列为后续工作" |
| "本地大模型部署" | 本身是**部署选型**，不是创新；且小模型稳定性是双刃剑 | 讲成"为离线与数据不出域做的取舍"，不列为创新点 |

## 4. 竞品对比

> 以下为**定性判断**，不含版本号、性能数据或未核实的引用来源。AI 辅助渗透类工具发展快、形态不一，故只作定性描述。

| 维度 | **sqlmap（含 tamper）** | **AWVS / Acunetix** | **Burp Suite（含插件）** | **OWASP ZAP** | **AI 辅助渗透类（PentestGPT 等，定性）** | **本项目** |
|---|---|---|---|---|---|---|
| Payload 生成方式 | 内置规则/字典 + 人写死的 tamper 变换函数 | 厂商私有规则库，随版本更新 | 人工构造 + 插件扩展 | 内置主动扫描策略 | 以对话/建议为主，输出思路与步骤 | 本地大模型**按每轮响应在线生成/变形** |
| WAF 绕过能力 | 有，但靠**预置 tamper 脚本**，需人选、可组合、不感知响应 | 有通用规避，策略封闭不可定制 | 靠人 + 插件，上限高但依赖经验 | 较弱，靠策略配置 | 通常不直接驱动绕过（推断） | **主打卖点**：反馈驱动的变形 |
| 闭环反馈 | **弱**：启发式/布尔盲注是"判定有无注入"的逻辑，不是"按 WAF 拦截反馈改写载荷"的生成逻辑 | 内部有，但对用户封闭 | 需自写扩展才有 | 有限 | 多为"人问机答"，非自动闭环（推断） | **核心差异点**：响应 → 模型 → 下一轮载荷 |
| 误报控制 | 规则为主，成熟稳定 | 厂商规则，成熟 | 人工确认，最可靠 | 规则为主 | 依赖人复核（推断） | 规则 + AI 语义双重判定（**待量化验证**） |
| 部署形态 | 本地 CLI，轻量 | 商业软件 / 服务端 | 本地客户端 + 插件生态 | 本地 / 开源 | 多为云端 API 对话（推断） | **本地 Ollama 全离线**，Web 平台 |
| 上手成本 | 低（命令行） | 低（图形化），但授权成本高 | 高（需专业经验） | 中 | 中（会提问即可） | 中低（网页提交 URL） |
| 受众 | 渗透工程师、自动化脚本 | 企业安全部门 | 专业渗透/红队 | 开发/安全入门、CI 集成 | 学习者、辅助参谋 | 自查人员、教学/竞赛演示 |
| 成熟度与覆盖面 | **很高**，漏洞类型覆盖广 | 很高 | 很高（生态） | 中 | 早期、形态未定（推断） | **低**：仅 3 类漏洞 + 自建靶场（推断） |

### 4.1 重点问题：sqlmap 的 tamper + 启发式检测，和「AI 闭环」到底差在哪

**差在"状态"和"决策者"，不在"变换技巧"本身。**

| 对比项 | sqlmap tamper + 启发式 | 本项目 AI 闭环（若真正做到） |
|---|---|---|
| 变换从哪来 | 人事先写好的、有限的变换函数集合 | 模型在线生成/组合 |
| 是否感知本次响应 | **否**，tamper 与响应无关、无状态，按预设顺序串联 | **是**，本轮的拦截关键词、状态码、拦截页语义是下一轮的输入 |
| 谁决定"下一个怎么变" | 人（选脚本、排顺序）或固定策略 | 模型（依据本轮反馈做策略决策） |
| 遇到没见过的 WAF 规则 | 需人工新增 tamper 脚本 | 理论上可泛化（**需实验证明，不能只靠说**） |
| 过程可解释 | 弱 | 强（逐轮日志 + 模型输出可展示） |

一句话：**tamper 是"离线预定义的无状态变换"，AI 闭环是"以响应为状态的在线策略收敛"。** 另外要澄清一个常被混淆的点——sqlmap 的**启发式检测 / 布尔盲注判定**解决的是"这里有没有注入"（判定问题），并不解决"WAF 把我拦了，我该怎么改载荷"（生成问题），两者不是同一件事，不能拿来当"sqlmap 也有闭环"的反驳。

### 4.2 这个差异够不够撑起一个项目？——分档判断

| 实现程度 | 判断 |
|---|---|
| 仅做到"模型替人挑/组合 tamper 技巧" | **撑不起核心创新**。这只是工程便利，应作为整合亮点讲，硬说成创新会被当场拆穿 |
| 做到"反馈驱动的策略收敛" + 对未预设 WAF 规则有泛化 + 有消融实验 | **足以撑起一个教学/竞赛级作品的创新点**，且"过程可解释 + 离线不出域 + 报告闭环"能构成完整产品叙事 |
| 声称"超越/替代 sqlmap" | **不成立**。覆盖面、稳定性、工程成熟度、漏洞类型数量均远不及（推断）；一句话讲"补充而非替代"最稳 |

**给答辩的定调建议**：把 sqlmap 设为**基线对照组**（这是对比演示已经在做的事），结论表述为"在 WAF 拦截这一特定条件下，闭环自适应相比静态 tamper 能显著降低假阴性"，而不是"我们比 sqlmap 强"。范围收窄，结论反而无可辩驳。

## 5. 需求池与人力分配评估

### 5.1 P0 / P1 / P2

| 优先级 | 需求 | 为什么是这个级别 |
|---|---|---|
| **P0** | 端到端闭环跑通一条完整链路（提交 URL → 采参 → 生成载荷 → 发包 → 采响应 → 反馈 → 下一轮 → 命中 → 判定 → 入库 → 前端展示），至少在自建带 WAF 靶场对 1–2 类漏洞成功 | 跑不通则整个作品不成立 |
| **P0** | **对比演示**：sqlmap 直跑被 WAF 拦、扫不出 → 本系统自适应绕过、成功检出 | 全项目唯一的"证明时刻"，缺了就没有说服力 |
| **P0** | 本地 Ollama 离线推理可用、断网可跑，零外部 API | 既是卖点也是比赛环境硬约束，现场翻车即崩 |
| **P0** | 大屏实时展示"当前 payload + WAF 拦截标记" | 评委直观看到"AI 在干活"的唯一窗口，比任何 PPT 都有效 |
| **P0** | **迭代日志 / 证据链留痕**：每轮请求包、响应、拦截判定、模型决策原文可查、可导出 | 直接应对"怎么证明不是硬编码"（见 6.3），是答辩命门 |
| **P0** | 漏洞结果页 + 至少能导出一版 PDF 报告 | 成果闭环，缺了像半成品 |
| **P0** | 授权与边界声明统一进申报书 / PPT / 讲稿 / 页面页脚 | 见第 1、7 部分，口径不一致即扣可信度分 |
| **P1** | 双重判定（规则 + AI 语义）+ 误报量化的小规模实验 | 支撑"降误报"从口号变结论 |
| **P1** | 消融实验、轮次—成功率收敛曲线 | 支撑创新成色（第 3.1） |
| **P1** | 三类漏洞（SQLi / XSS / 文件上传）全覆盖 | 完整度加分，但可先保 1–2 类 |
| **P1** | 报告对标等保风格的完整度、在线预览、历史记录页 | 产品完整度 |
| **P1** | 一键部署包、并发与超时控制 | 可复现性加分 |
| **P2** | 站内深度爬虫（可用单页 / 指定参数列表替代） | 演示用靶场页面少，收益低 |
| **P2** | UI 动效精修、多主题、图标体系 | 竞赛时间紧，专业感够用即可 |
| **P2** | 报告模板多样化、并发规模优化、更大规模绕过技巧库 | 锦上添花，可砍 |

> 收缩建议：若时间紧，**P0 里只保"1 类漏洞 + 1 个 WAF 规则 + 完整日志 + 对比演示"**，把 P1 全砍也仍能成立；反之若砍掉"迭代日志"或"对比演示"，创新与可信度会同时失守。

### 5.2 四人分工评估

| 成员 | 承担 | 负荷判断 | 主要风险 | 建议调整 |
|---|---|---|---|---|
| **1 号（组长）** | AI 核心层 5 子模块 + 靶场搭建 + Ollama 提示词 + 测试用例 + 技术文档 | **严重过载**，且是全队唯一技术风险集中点（单点故障） | 决定创新成立与否的**消融实验、泛化测试、证据链**也压在他身上；一旦他卡住，全队停摆 | 把**靶场搭建 / 测试用例 / 部分提示词**标准化后分出去；让 4 号承担"迭代日志存取接口"，把 1 号从工程杂活里解放出来专注闭环与实验 |
| **4 号（前后端）** | 5 个前端页面 + 业务调度 + MySQL + PDF 导出 + 一键部署 + 对接 AI 接口 | **偏重**，但工作可裁剪 | 强依赖 1 号接口稳定；接口一变，前后端全返工 | **尽早定死接口契约**（任务 ID、轮次日志结构、判定结果格式）；P2 的 UI 精修明确砍掉 |
| **2 号（主讲）** | 熟悉架构、讲稿、答辩题库、彩排 | **开发期明显不饱和，答辩期关键** | 若不早期介入技术细节，答辩题库会空，现场答不出第 6 部分的尖锐问题 | 从第一周就跟着 1 号同步架构与实验数据，把"尖锐问题应对"当作**持续产出**而非答辩前突击 |
| **3 号（文档美工）** | 架构图美化、PPT、申报书、展板、前端 UI 设计 | **前/后忙、中期可能闲置** | "UI 设计"与 4 号"前端实现"边界不清 → 返工；另需承担第 1 部分的**口径核对** | 明确 3 号只出**设计稿/视觉规范**、4 号负责实现；把"全套材料用词统一检查"列为 3 号的正式交付项 |

**整体判断（推断）：**
- **技术风险单点化**：创新成立与否全系于 1 号一人，缺备份、缺文档沉淀，是本项目最大的组织风险。
- **节奏风险**：2、3 号的产出集中在后期，容易出现"前期都闲、答辩前一周全挤在一起"，且届时 1 号还在改代码、没人有精力陪 2 号彩排。
- **建议设一个中期里程碑**：「闭环跑通 + 对比演示录屏 + 迭代日志可导出」作为全队对齐点，在此之前 2 号开始写题库、3 号定视觉规范与口径表，把后期压力前移。

## 6. 评审视角：最可能被追问的尖锐问题与应对

| # | 评委可能怎么问 | 应对思路（要点，不是逐字稿） |
|---|---|---|
| 1 | **"这不就是套壳调大模型吗？把 GPT 套了个壳。"** | ① 不否认模型是工具，把价值锚定在**闭环控制与反馈状态设计**（状态怎么定义、模型输出怎么被校验、如何进入下一轮）；② 出示**消融实验**：去掉反馈 / 去掉模型后成功率与收敛轮数明显变差，证明模型不是装饰；③ 展示提示词与状态机设计，说明载荷依据**是本轮响应**而非模板库；④ 补一个**未预设过的 WAF 规则**上的泛化测试 |
| 2 | **"和 sqlmap 的 tamper 到底有什么区别？"** | ① 一句话讲本质："tamper 是无状态、与响应无关、人写死的变换；我们是以响应为状态、模型在线决策的策略收敛"；② 澄清启发式检测属于**判定**不是**生成**；③ **不硬刚"超越"**，主动把 sqlmap 设为基线对照组，结论收窄为"WAF 拦截条件下降低假阴性"；④ 承认覆盖面与成熟度远不及，定位为补充增强 |
| 3 | **"怎么证明不是提前硬编码好的演示？"** | ① **现场 live 跑，不播录像**；② 请评委**随机指定**参数 / 换一个未预设的注入点或 WAF 规则；③ 开放**逐轮迭代日志**（每轮载荷由哪条响应触发、模型输出原文、时间戳），证明载荷是当轮生成的；④ 提供可复现的录屏与日志备查 |
| 4 | **"'降低误报'怎么量化？凭什么这么说？"** | ① 定义清楚降的是哪类误判（把"被 WAF 拦截"当成"有漏洞/无漏洞"、把正常响应当异常）；② 给标注集 + 混淆矩阵（TP/FP/FN）+ 与"纯规则判定"基线对比；③ **不编数字**；样本不足就如实说明是小样本验证、列为后续工作，坦诚比夸大更安全 |
| 5 | **"本地小模型能稳定生成可用载荷吗？断网、性能、现场翻车怎么办？"** | ① 坦承小模型稳定性是**真实短板**，不回避；② 用**实测**（而非估计）给出成功率、收敛轮数、单轮耗时区间与现场机器配置；③ 说明工程兜底：规则校验 + 兜底载荷集 + 轮次上限 + 超时控制，保证演示可复现；④ 把"离线不出域"讲成**取舍**（牺牲模型能力换数据安全与断网可用），不是纯优势；⑤ 准备人工兜底预案，避免现场卡住 |

> 补充（选备）：若被问"这东西会不会被拿去做未授权攻击"，直接引到第 7 部分的边界声明，**主动先讲比被追问更好**。

## 7. 合规与伦理边界（务实，点到为止）

| 边界项 | 产品/材料层面怎么落地 |
|---|---|
| **授权测试** | 只用于自己拥有或已获**书面授权**的目标。建议在任务配置页加**必填的授权确认勾选项**，并把授权标识写入任务表留痕，让"授权"成为**可追溯的产品字段**，而非一句口头声明 |
| **靶场自测** | 演示一律在 DVWA / 自建带 WAF 靶场进行；答辩材料明确标注"演示环境为本地隔离靶场"；不出现任何真实域名、IP 或真实站点截图 |
| **不对未授权目标使用** | 申报书、PPT、展板、讲稿统一加边界声明；全程使用"探测 / 验证 / 授权测试"措辞，禁用"AI 自主攻击"类表述（与第 1.4 用词表一致） |
| **数据留存风险** | 系统留存完整请求包/响应包，可能含 Cookie、Token、业务数据 → 建议**脱敏后入库/导出**，并限定留存范围与访问 |
| **报告输出风险** | 导出的"成功绕过载荷"与请求/响应证据属敏感内容 → 报告标注"仅限授权范围内使用"、控制分发，必要时加密级/水印标识 |
| **答辩材料如何体现** | ① 首页与页脚固定一行："授权自测工具，不用于未授权目标，不涉及未知漏洞挖掘"；② 单设一页「合规与边界」（授权、靶场、脱敏、不涉 0day）；③ **讲稿开头主动先讲边界**，把评委的伦理质疑提前化解，反而显得团队成熟；④ 与第 1.4 统一口径严格一致 |

> 本部分仅讨论产品设计与材料呈现边界，不提供任何针对真实系统的操作指引。
